# CCCP Reference Implementation 开发日志 · v0.2.0

日期：2026-09-17—20  
状态：Host Runtime M0—M4 实现里程碑完成；CCCP Protocol 1.0 语义保持冻结。

## 版本结论

本轮将 `cccp-reference` 从 `0.1.1` 提升为 `0.2.0`。升级依据是 Host Runtime 已从协议核心之外的设计方案落实为可运行参考实现：M0/M1 的六端口和认证边界、M2 的 SQLite 持久化与恢复、M3 的 Docker 隔离与 Git worktree、M4 的真实 Codex 实施与独立 R3 已形成闭环。

这不是 CCCP Protocol 1.1。Envelope、Schema、生命周期、Human Authority、Decision、Delegation、Review 和 `DONE` 的语义仍为 CCCP 1.0；只有既有 `acceptTask` 的真实 Human 路径可以完成任务。

## 起点、问题定义与架构取舍

本轮开始时，CCCP 已有 Protocol Core、Controller、Adapter、Discovery、Review 与审计规则，但“由宿主保证”的身份、模型、工具、持久化、工作区和恢复责任仍分散在文档假设中。上一轮 Host Runtime 规划把该缺口定义为 Protocol Core 之上的 Runtime Plane：Core 继续判断谁能做决定、什么状态可以转移、何时需要 R1/R2/R3；Runtime 只负责把真实世界的请求、身份、模型与工具接到这些既有规则上。

这个边界决定贯穿 M0—M4，避免了三种看似方便但不可接受的做法：

1. 不把 SDK、Docker、SQLite 或模型调用放入 Lifecycle Controller，避免供应商机制改写 CCCP 语义。
2. 不允许 Agent 取得 Controller、审批、Delegation、命令行、环境变量或宿主回调；模型只返回候选结构化数据。
3. 不把“模型说已完成”“容器命令退出”或“网络请求报错”当作真实世界已停止的证明；无法确认时保留记录并 fail-closed。

最终实现沿用了规划中的六端口：`IdentityProvider` 认证调用方，`AgentProvider` 生成候选，`ToolRunner` 产生受限副作用，`WorkspaceManager` 固定仓库与租约，`EvidenceStore` 保存可验证 Artifact，`StateStore` 保存可恢复状态。`HostRuntime` 只做受认证的编排和绑定；Controller 仍是状态改变的唯一入口。

| 所属层 | 本轮职责 | 明确不承担的职责 |
|---|---|---|
| Protocol Core / Controller | Human Authority、Decision、Delegation、Review、状态转移、Revision 和 DONE 守卫 | 启动模型、运行 Docker、保存数据库连接、猜测真实进程状态 |
| Adapter | Discovery freshness、操作域和路径授权、执行前守卫 | 认证用户、授予模型权限、绕过已尝试操作 |
| Host Runtime | 身份解析、端口装配、上下文绑定、run/operation 记录、恢复协调、Artifact 绑定 | 自行批准 Decision、推导新的 Delegation、将模型输出当作事实 |
| Provider / Store | 真实或模拟的受限实现、存储和查询 | 推进 Controller、伪造 Human、修改协议状态 |

## M0—M4 实现过程

### M0：冻结基线与运行时 contract

M0 把 Runtime 数据结构与 Protocol Schema 分开维护。请求统一包含 credential、任务上下文、payload 与幂等键；上下文固定 task、authenticated principal、state version、Delegation、workspace 和 correlation。Runtime contract 拒绝函数、稀疏数组和伪造 actor 字段，避免未序列化对象或消息中的角色声明穿透到 Host。

同时建立 fake Agent、fake ToolRunner、内存 State/Evidence/Identity/Workspace 装配。它们只用于验证接口、幂等、审计和生命周期协作，能力 manifest 明确标记为 simulation，不能声称 crash recovery、真实 Agent、OS sandbox 或独立 R3。

### M1：受认证编排与模拟工作流

M1 使 `HostRuntime.create()` 在启动时验证六端口的方法面和 capability 组合。所有调用先通过 IdentityProvider 取得 principal，再检查 task、workspace、Delegation 和 Controller `state_version`；请求中的 `actor`、序列化 approval 或伪造 Review 都不能改变权限。

实现了单进程 CAS、idempotency receipt、in-flight coordination、Human Stop 与迟到结果隔离。模拟 Agent 可以提出 implementation/report/review 候选，但 Agent 候选本身不会推进 Controller，也不能把 simulation 输出包装成真实 Evidence。

### M2：SQLite 持久化、审计与恢复

M2 将 task snapshot、Controller event、runtime audit、operation、Agent run、Artifact 与凭证哈希持久化到 SQLite。恢复不反序列化并信任任意“完整 Controller”对象，而是按既有公共生命周期接口重放 journal，并校验审批、版本、Evidence 与审计链。

该阶段还加入 Store revision CAS、outbox/inbox 的不确定投递记录、进程死亡后的 lease 获取，以及“未知副作用不自动重试”的规则。数据库写入失败时 Host 停止继续该任务，但仍允许 Human Stop；这保证恢复故障不能反向制造权限或取消 Human 的停止决定。

### M3：Docker 工具、Git worktree 与真实副作用

M3 以固定 digest 镜像建立 `ProcessToolRunner`。Tool binding 预先声明绝对 argv、允许路径、读写属性、资源限制和网络隔离；Agent 文件候选经路径、大小、重复项和 Delegation 校验后，作为 JSON stdin 数据传给固定容器命令，不能变成宿主 shell 命令、环境变量或挂载参数。

工作区使用 Git worktree 固定 commit，并通过持久租约限制写者。真实执行创建 DIFF 与 TEST_RUN Artifact，分别绑定 operation、task、principal、repository before/after snapshot、内容 hash 和可重算 artifact reference。容器超时、非零退出、输出洪泛、detached 子进程和 Host SIGKILL 都进入 `FAILED_CLEAN`、`EFFECT_UNKNOWN` 或 `INTERRUPTED` 的明确路径，而不是被压缩成“失败后可重试”。

### M4：真实 Agent、独立 R3 与 E2E

M4 接入只读的 Codex App Server implementer。它返回结构化 ImplementationReport 与完整候选文件内容，不能直接修改工作区；Host 校验后才由 M3 Docker binding 应用。独立 Review 使用不同 principal、provider instance、外部 thread/turn 或 response binding，并只收到 Host 重新构建的 frozen Decision、Specification、report、repository snapshot 和已验证 Artifact。

ChatGPT App Server 是默认的验收 Reviewer。OpenAI Responses Provider 支持保存的 background response、远端 status/reconcile；DeepSeek Responses Provider 则明确实现为无状态同步后端，不声明其 API 不具备的远端查询、cancellation 或 recovery 能力。Routed provider 只有在 implementer 与 reviewer 都为真实、且 reviewer 显式声明独立边界时，才公开 `real_agents` 与 `independent_r3` capability。

## 本轮 R3 修复

独立架构审查首先给出 `REVISION`，指出三项边界问题：Host 拒绝的 Agent 输出可能被复用；外部 Agent 传输失败后的状态可能绕过 reconciliation；未证实停止的工具执行可以在同一 Host 继续推进。

修复后，Agent 输出需完成本地 schema、identity、Delegation 和 frozen-evidence 校验，并被标记为当前 execution cycle 的 `accepted`，才能成为 Tool、DIFF 或 R3 的输入。真实 Agent 和工具只要没有停止证明，恢复、resume、后续 dispatch 和 Host close 都 fail-closed。R3 提交还必须逐项匹配其运行时冻结的 Artifact 集合，并由不同 principal/provider instance/外部运行边界的 Reviewer 产生。

DeepSeek 的真实 API 测试还暴露模型会自行填写 reviewer 标识或引用示例字段。Provider 因而把 reviewer principal 和 review level 绑定到认证请求上下文，并强化“仅可逐字引用输入 artifact_ref”的结构化指令；Host 保留独立的二次校验。

### 修复项与安全意义

| 发现 | 风险 | 修复 | 回归验证 |
|---|---|---|---|
| Host 拒绝的 Agent 输出仍可被下游按 `COMPLETED` 查到 | 迟到、格式错误或越权候选可能驱动工具或 R3 | 只有全部 Host 校验通过的 run 才写入 `accepted=true` 与当前 cycle；Tool、DIFF 和 R3 都要求 accepted run | 停止后迟到 Agent 输出、拒绝 R3 输出不能换 Evidence 重提 |
| 带外部 binding 的 FAILED/INTERRUPTED Agent run 可能跳过恢复对账 | 外部回合可能仍在执行，Host 却恢复任务 | 未有停止证明的真实 run 在 recover、resume、dispatch 和 close 前均要求 reconcile | transport-failed 与 RUNNING Agent 都在未证明停止时 fail-closed |
| `EFFECT_UNKNOWN` 工具在同一 Host 内可经 Discovery 后继续 | 旧容器/进程的副作用无法确认，可能并发或重放 | resume 与下一次 Tool dispatch 先 reconcile 所有未知 operation | live tool reconciliation 用例要求停止证明后才可继续 |
| R3 运行后提交时可改变证据集合 | Reviewer 实际看到的证据与提交给 Controller 的证据不一致 | accepted R3 保存 frozen artifact refs，提交必须集合完全相同 | 拒绝的 R3 output 不能用另一套 refs 提交 |
| Reviewer 身份由模型 JSON 自报 | 模型可填写 Human、示例或错误 identity | Provider 从认证 `context.principal` 绑定 reviewer/review_level；Host 再验 | DeepSeek 实际 API contract 和 provider 单测 |

## 真实验证记录

本轮默认验证通常为 `npm test`：204 tests 中 194 PASS、0 FAIL、10 个明确 opt-in 的外部环境测试 SKIP。`npm run check` 通过 9 个 schema/state artifacts，`git diff --check` 通过。版本日志收尾时，一次并行 `npm test` 在 Windows 临时仓库的 `.git/index` 上遇到 `Permission denied`；即时重跑 `tests/hardening.test.mjs` 为 16/16 PASS，串行完整回归 `node --test --test-concurrency=1` 为 194 PASS、0 FAIL、10 SKIP。该现象记录为 Windows 临时 Git 文件锁观察项，未被重写成成功，也尚未作为协议或 Runtime 边界缺陷修改实现。

在 Windows、Node 24.19.0、Docker Desktop Linux Engine 29.8.0、固定镜像 `node@sha256:50c8e8ca1d27439048670df5883f32d57cf81cff6233222c893fd0d9884cbd81` 下，真实 Docker 集成 8/8 通过。升级到 Codex CLI `0.155.0-alpha.9.2` 后，使用 `gpt-5.5` 执行真实 Codex + ChatGPT E2E：正常路径 86.2 秒通过，强制 Host 崩溃恢复路径 85.1 秒通过；两条路径均确认没有遗留 CCCP 标记容器。

## DeepSeek 组合的已知问题

`DeepSeekReviewProvider` 的单独真实结构化 API contract 已通过，但“真实 Codex + DeepSeek 完整 M4 E2E”尚未形成可重复 PASS，必须记录为已知限制：

1. 更新前的 Codex CLI 对默认 `gpt-6-astra` 返回客户端版本不兼容；更新后该错误消失。
2. 使用 `gpt-5.5` 时，正常路径曾在真实 Codex 回合五分钟后超时。Host 正确拒绝在未证明远端停止时释放 lease。
3. 恢复路径曾到达 R3，但 DeepSeek 的判断使 Controller 进入 `REVISION`，未达到 `HUMAN_ACCEPTANCE`。这不是通过结果，也没有被测试代码覆盖为 PASS。

因此 DeepSeek 当前定位为开发期、低成本的结构化 Review 接线与 API contract 后端；不能替代已经通过的 ChatGPT 独立 R3 M4 验收。后续应单独分析 DeepSeek 的完整 R3 prompt、模型选择、超时与拒绝结论，不降低 Artifact、Authority 或 recovery 边界来迁就模型输出。

## 未完成项与发布边界

- 本轮 M4 源码、设计和审计材料仍需要按 [M4 R3 审查交接](../M4_R3_HANDOFF.md) 进行最终独立源码审查；运行时 R3 E2E 不等同于该审查。
- 最终 `DONE` 仍需要 Human 明示接受，当前真实 E2E 故意停在 `HUMAN_ACCEPTANCE`。
- M5 的多任务调度、完整 capability negotiation、Threat Model、外部 Conformance、CI/release 与生产级身份管理不属于 v0.2.0。
- Windows 并行默认测试曾出现一次临时 Git index 文件锁；串行回归已通过。后续应在 CI 中持续观测，并决定是否需要对临时仓库创建或 Git index 访问做专门的并发隔离，而不是把测试脚本静默改成跳过该路径。

v0.2.0 的含义是“可运行、可恢复、可隔离并可真实验证的 CCCP 1.0 Host Runtime 参考实现”，不是生产部署承诺，也不是对 DeepSeek 全链路稳定性的声明。
